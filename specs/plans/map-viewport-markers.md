# План: карта — маркеры по зоне видимости, сессионный кэш и фильтры

**Дата:** 2026-11-23  
**Статус:** реализовано; unit-тесты, сборка и ручная проверка на Pixel_10_Pro_Fold выполнены  
**Задача:** `MAP-01` в [docs/to-do.md](../../docs/to-do.md)  
**Подзадачи:** `MAP-01a` … `MAP-01f` (см. «Порядок реализации»)  
**Ограничение:** только карта и маркеры. Лента, профиль, соцсеть и достижения в этот план не входят.

## Обзор

Сейчас карта загружает **все** публичные отчёты одним запросом и хранит их в Room. При
росте данных это первое место, которое начнёт деградировать. Кроме того, чипы фильтров
на карте зависят от загруженных маркеров, а фильтр «Избранное» на вкладке «Карта»
фактически не работает: `MainShell` не передаёт `favoriteReports`, поэтому чип
показывает пустой экран.

Цель плана:

1. Публичные маркеры грузить только для видимой области экрана.
2. Не грузить и не показывать маркеры ниже порога зума.
3. Держать загруженные маркеры в памяти на время пребывания на карте с текущим
   фильтром; не удалять старые при панорамировании.
4. Перенести фильтры в отдельный экран и применять их на сервере.
5. Убрать постоянный кэш маркеров из Room; офлайн оставить только свои маркеры из
   `report_details`.
6. Убрать избранное с карты.

## Принятые решения

| № | Решение |
|---|---|
| 1 | Публичные маркеры — только онлайн, запрос по bbox видимой зоны. |
| 2 | Порог зума — `10.0`. Ниже порога маркеры не запрашиваются и не рисуются; кэш при этом не чистится. |
| 3 | Лимит ответа — `300` маркеров на зону. |
| 4 | Дебаунс после остановки камеры — `350 мс`; запас вокруг bbox — `25%`. |
| 5 | Сессионный кэш маркеров живёт в `MapCoordinator` в памяти, без Room. |
| 6 | Кэш — `Map<UUID, MarkerDomain>`: дубликаты по `id` обновляются, а не добавляются. |
| 7 | Потолок кэша — `2000` маркеров; при переполнении вытесняются самые далёкие от текущего центра. |
| 8 | При панорамировании и изменении зума накопленные маркеры не удаляются. |
| 9 | При смене фильтра и при уходе с вкладки «Карта» кэш очищается и данные грузятся заново. |
| 10 | При переходе в деталь отчёта и возврате назад кэш **не** очищается. |
| 11 | Свои маркеры берутся из `report_details` (офлайн) и фильтруются на клиенте. Публичные — только из сети. |
| 12 | Постоянный кэш маркеров удаляется: таблица `markers`, `MarkerDao`, `MarkerStore`, `MarkerCacheCleaner`, записи из `ReportWriter`/`ReportDetailsStore`, очистка в `SupabaseAuthRepository`. Room 14 → 15. |
| 13 | Фильтры — отдельный экран «Фильтр поиска» по макету Figma. Применение — галочкой в app bar, не на каждый тап; back без применения отменяет черновик. |
| 14 | Серверная фильтрация в запросе маркеров + клиентская проверка `ReportFilters` как страховка и для офлайна. |
| 15 | Фильтр по рыбе — мультивыбор по `species_id` из каталога `fish_species`, максимум 3 вида. Выбранные виды показываются input-чипами внутри поля; метка «Поиск» видна всегда. |
| 23 | Способ ловли — мультивыбор только на карте (`fishing_method in (...)`); в поиске по отчётам остаётся одиночный выбор. |
| 16 | Избранного на карте нет. Вместо него — «Мои отчёты»: показывать только свои маркеры из `report_details`, публичные при этом не запрашиваются. |
| 17 | Фильтр по дате в карту не входит (расхождение с первой редакцией плана, зафиксировано по макету). |
| 18 | Чипы на карте (`FishingFilterChips`) убираются из первой версии; быстрые чипы — отдельное решение после запуска. |
| 19 | Full-map из детали отчёта не использует viewport-режим и строит маркер из самого отчёта. |
| 20 | Supabase в первой версии не меняется: RLS `fishing_select` уже отдаёт `is_public = true`. |
| 21 | Кластеризация в первую версию не входит. При достижении лимита показывается подсказка «Приблизьте карту». |
| 22 | Тайлы карты кэшируются средствами osmdroid; публичные маркеры офлайн не сохраняются. |

## Цели

1. Карта не делает запрос «все публичные отчёты».
2. Количество маркеров в памяти ограничено.
3. Пользователь не видит «мигания» при панорамировании: ранее загруженные маркеры
   остаются на месте.
4. Фильтры карты не зависят от того, что попало в текущую зону.
5. Кодовая база избавляется от постоянного кэша маркеров и связанных с ним тестов.
6. Свои отчёты остаются доступны на карте без сети.

## Поведение (UX)

| Событие | Поведение |
|---|---|
| Открыл вкладку «Карта» | Загружается текущая зона; камера восстанавливается из `mapLastCenter*`. |
| Подвинул карту | Через 350 мс загружается новая зона; маркеры **добавляются** к накопленным. |
| Вернулся в ранее посещённую зону | Маркеры уже в памяти и сразу рисуются; при необходимости тихо обновляются. |
| Зум ниже 10 | Маркеры скрыты, запросы не выполняются, накопленное не чистится. |
| Применил фильтр | Кэш очищается, текущая зона грузится заново. |
| Ушёл на другую вкладку | Кэш очищается, запросы отменяются. |
| Вернулся на карту | Камера на прежнем месте, маркеры грузятся заново. |
| Открыл деталь отчёта и вернулся | Кэш и камера сохраняются. |
| Ошибка сети при непустом кэше | Маркеры остаются, показывается снекбар с повтором. |
| Ошибка сети при пустом кэше | Полноэкранное состояние ошибки с повтором. |
| Достигнут лимит 300 | Показывается «Показаны не все отчёты, приблизьте карту»; зона не считается полностью загруженной. |
| Нет сети, своих маркеров нет | Подсказка «Нет сети. Показаны только ваши отчёты» (если своих нет — текст без обещания маркеров). |

### Состояния оверлея

`MapOverlayState` расширяется:

- `Loading` — первая загрузка, кэша нет; состояние есть, плашка не показывается.
- `Error` — первая загрузка не удалась.
- `ZoomedOut` — зум ниже порога; состояние есть, но плашка не показывается (чистая карта).
- `Empty` — успешный ответ, отчётов нет вообще; плашка не показывается.
- `ViewportEmpty` — в кэше есть маркеры, но в текущей зоне нет; плашка не показывается.
- `FilteredEmpty` — маркеры в зоне есть, но ни один не проходит фильтр; состояние
  есть, плашка не показывается.
- `None` — маркеры отображаются.

## Архитектура и поток данных

```
Карта (MapScreen)
  └─ MapListener onScroll / onZoom / onFirstLayout
       └─ MainViewModel / MapCoordinator.onViewportChanged(bounds, zoom)
            ├─ зум < 10 → отменить запрос, ничего не грузить
            ├─ зона внутри последней загруженной (+25%) → ничего не грузить
            ├─ debounce 350 мс, отмена предыдущего запроса
            ├─ FishingRepository.loadMapMarkers(bounds, filters)
            │    └─ ReportRemoteQueries.fetchPublicMapMarkers(...)
            └─ merge в Map<UUID, MarkerDomain> → опубликовать список

Свои маркеры
  └─ ReportDetailsDao.getOwnMapMarkers(userId) → Flow<List<MarkerDomain>>
       └─ фильтрация ReportFilters на клиенте → merge при отображении
```

### Состояние `MapCoordinator`

- `accumulated: Map<UUID, MarkerDomain>` — сессионный кэш публичных маркеров.
- `loadedViewport: BoundingBox?` — последняя успешно загруженная зона.
- `truncated: Boolean` — последний ответ упёрся в лимит.
- `activeFilters: ReportFilters`.
- `isLoading`, `isRefreshing`, `error` — как сейчас.
- `mapLastCenterLat/Lon/Zoom` — сохраняются.

### События

- `onMapShown()` — вкладка карты стала активной. Если кэша нет, инициировать загрузку
  текущей зоны после первого layout.
- `onMapHidden()` — уход с вкладки. Отменить запросы, очистить `accumulated` и
  `loadedViewport`.
- `onViewportChanged(bounds, zoom)` — основная точка входа загрузки.
- `onFiltersApplied(filters)` — очистить кэш, применить фильтры, загрузить текущую зону.
- `onRefreshRequested()` — очистить кэш и загрузить текущую зону (повтор/«Обновить»).

`MainViewModel.selectTab(index)` вызывает `onMapShown()`/`onMapHidden()` при переходе
на/с индекса карты. Переход в деталь отчёта вкладку не меняет, поэтому кэш сохраняется.

## Контракт данных

### Публичные маркеры

Новый запрос в `ReportRemoteQueries`:

- фильтр `is_public = true`;
- диапазон `water_lat` между `south` и `north`, `water_lng` между `west` и `east`;
- применённые фильтры (см. таблицу ниже);
- `limit = 300`;
- без сортировки по `fishing_start_at`, чтобы не мешать индексу;
- рыба — через `fishing_fish!inner(*, fish_species(canonical_name))`;
- ответ — `RemoteMapMarker` + флаг «достигнут лимит» (определяется по количеству
  строк, как в остальных запросах проекта: запрашивать `limit + 1`).

`MarkerDomain` остаётся UI-моделью. `MarkerEntity` удаляется.

### Фильтры → запрос

| Фильтр | Серверное условие |
|---|---|
| Трофей | `type = 'HAUL'` |
| Платный водоём | `water_paid = true` |
| Метод (мультивыбор) | `fishing_method in (<значение1>, <значение2>, …)` |
| Рыба (мультивыбор) | `fishing_fish!inner` + `species_id in (<id1>, <id2>, …)` |
| Мои отчёты | **не серверный фильтр**: публичные маркеры не запрашиваются, показываются свои из `report_details` |

Клиент дополнительно применяет `ReportFilters.matches` к `MarkerDomain`. Для этого
`MarkerDomain.fishNames` должен содержать канонические имена из `fish_species`.
Отчёт проходит, если совпал хотя бы один выбранный вид. Фильтр по рыбе не покажет
отчёты со свободным вводом, для которых `species_id` не разрешился, — это осознанное
поведение, зафиксировать в тексте пустого состояния.

### Свои маркеры

- Новый запрос `ReportDetailsDao.getOwnMapMarkers(userId): Flow<List<OwnMarkerRow>>`
  или маппинг `ReportDetailsEntity` в `MarkerDomain`.
- В `report_details` уже есть `waterLat/Lng`, `waterPaid`, `type`, `fishingMethod`,
  `fishingStartAt`, `isPublic`, `fishJson`.
- Рыба для фильтра: `speciesId` из `fishJson` → каноническое имя через кэш
  `FishCatalogRepository`. Если `speciesId` нет — сравнение по исходному имени.
- Свои маркеры не удаляются при смене фильтра и не участвуют в лимите/bbox.

### Ограничения

- Даталиния не поддерживается: bbox считается простым min/max по широте и долготе.
  Для Беларуси и соседних регионов это корректно.
- Отчёты без координат воды в выборку не попадают. На клиенте больше не подставляем
  `0.0` для карты.
- Координаты маркера — `water_lat/water_lng`; `spot_lat/lng` на карте не используются.

## Экран «Фильтры»

- Новый маршрут `MapFiltersRoute` (тип-безопасный, как `ReportListSearchRoute`).
- Открывается с карты по иконке «Фильтры» в app bar рядом с поиском, с бейджем
  количества активных условий.
- Состояние-черновик: изменения не влияют на карту до нажатия галочки «Применить».
- «Применить» — галочка в app bar; «Сбросить» — иконка refresh в app bar,
  показывается при активных условиях. Back без применения отменяет изменения.
- Состав первой версии: рыба (мультивыбор через `ExposedDropdownMenuBox`:
  можно печатать в поле, список фильтруется по каталогу `fish_species`;
  выбранные виды показываются input-чипами внутри поля, максимум 3;
  метка «Поиск» видна всегда), метод (мультивыбор), трофей, платный водоём,
  «Мои отчёты».
- Даты и избранного в фильтрах карты нет.
- После «Применить»: `MainViewModel.applyMapFilters(filters)` →
  `MapCoordinator.onFiltersApplied(filters)`.
- Состояние фильтров живёт в `MainViewModel` (переживает поворот). Process death
  сбрасывает фильтры — допустимо для первой версии; `SavedStateHandle` — отдельное
  улучшение.
- Чипы на карте и `uniqueFish` из `MapScreen` удаляются.

## Full-map из детали отчёта

- `MapScreen` получает флаг `viewportMode` (или определяет режим по `initialReportId` /
  `onBackClick`).
- В full-map режиме: viewport-загрузка отключена, фильтры не применяются, маркер
  строится из самого отчёта, а не ищется в кэше маркеров.
- Это чинит текущую зависимость от `mapMarkers.firstOrNull { it.id == id }`.

## Ошибки и офлайн

- Ошибка загрузки зоны при непустом кэше: сохранить маркеры, снекбар «Не удалось
  обновить карту», повтор.
- Ошибка первой загрузки: полноэкранное состояние с повтором.
- Офлайн: свои маркеры из `report_details`; публичные отсутствуют. Показать баннер
  «Нет сети. Показаны только ваши отчёты», если свои есть.
- Тайлы: osmdroid кэширует подложку сам; дополнительных действий в этой задаче нет.
- Устаревший приватный маркер живёт до ухода с вкладки/смены фильтра; открытие детали
  делает авторитетную проверку и скрывает отчёт.

## Тесты

### Unit

- bbox: расширение на 25%, `contains`, пропуск запроса внутри загруженной зоны.
- порог зума: ниже 10 — нет запросов, нет отображения, кэш не очищен.
- дебаунс/отмена: быстрые перемещения дают один запрос.
- накопление: A → B → A не очищает A; дубликаты по `id` не размножаются.
- потолок: больше 2000 — вытесняются дальние от центра, размер не превышает лимит.
- лимит ответа: `truncated` не помечает зону загруженной; показывается подсказка.
- очистка: `onFiltersApplied` и `onMapHidden` очищают кэш; переход в деталь — нет.
- маппинг фильтров в запрос: трофей, платный, метод, рыба.
- «Мои отчёты»: свои маркеры без запроса публичных.
- свои маркеры: маппинг из `report_details`, фильтрация, канонические имена рыб.
- ошибка: кэш сохраняется.

### UI / Compose

- `MapOverlayStateTest`: новые состояния `ZoomedOut`, `ViewportEmpty`.
- `MapScreen`: ниже порога — подсказка, маркеров нет; выше — маркеры.
- Экран фильтров: «Применить» меняет фильтры и триггерит загрузку; «Сбросить»
  очищает; back без применения не меняет состояние.
- «Мои отчёты» переключает источник на свои маркеры и не делает запрос публичных.
- Рыба: не больше 3 чипов; при лимите остальные пункты меню недоступны.
- На карте нет чипа «Избранное» и нет `uniqueFish`.
- `FullMapRoute`: маркер строится из отчёта, даже если его нет в кэше.

## Риски и открытые вопросы

- **Память.** Потолок 2000 и вытеснение дальних — компромисс. При плотных регионах
  лимит может срабатывать часто; кластеризация — следующий шаг.
- **Лимит 300.** Часть маркеров в густой зоне не загрузится; подсказка обязательна.
- **Устаревшие маркеры.** Приватный/удалённый отчёт может жить до смены фильтра/ухода
  с вкладки; деталь делает авторитетную проверку.
- **Алиасы рыб.** Свои маркеры в `report_details` хранят исходные имена; для фильтра
  нужен резолв через `speciesId` и каталог. Покрыть тестом.
- **Свободный ввод рыбы** без `species_id` не участвует в серверном фильтре по рыбе.
- **Порог зума 10** подобран по масштабу Беларуси; проверить на устройстве и при
  необходимости вынести в константу с быстрым изменением.
- **Даталиния** не поддерживается — осознанно.
- **Process death** сбрасывает фильтры и кэш; камера тоже не сохраняется в
  `SavedStateHandle` (текущее поведение). Улучшение — отдельно.
- **Офлайн публичных маркеров больше нет** — принятое решение. Если понадобится,
  вернуться к региональному кэшу с TTL, но не в этой задаче.
- **Supabase.** В первой версии изменений нет. Индекс
  `(water_lat, water_lng) where is_public` и денормализация `species_ids` на `fishing`
  — отдельная задача после роста данных; перед изменением схемы выполнить `AUD-09b`
  (baseline + RLS-проверки).
